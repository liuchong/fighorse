01 / 为什么是 fighorse

不是更多数据。
是更好的证据。

截图遗漏结构，原始 JSON 淹没上下文，黑盒工具难以调试。fighorse 在它们之间建立一条白盒、可检查、可脚本化的数据管道。

CAP / 01

设计包

一个高级接口汇总节点结构、设计令牌、截图、资产计划、实现风险和下一步诊断。

 CAP / 02

资源目录

先盘点团队、项目、文件、分支和设计库，再选择真正要实现的节点。

 CAP / 03

视觉审计

把应用截图与 Figma 参考纳入反馈循环，明确布局、字体、裁剪和安全区域差异。

 CAP / 04

资产清单

导出图片、组件和图片填充时附带 manifest，让下游工具读取事实而不是猜文件名。

 CAP / 05

Code Connect

生成、解析、验证、预览和发布现代模板，同时保持本地代码不被隐式执行。

 CAP / 06

Canvas Bridge

通过本地 Figma 开发插件创建和修改原生节点，每一层写权限都需要显式开启。
02 / 产品原则

CLI 为核。
MCP 为壳。

同一套能力既能被开发者从终端检查，也能被 Cursor、Codex、Kimi、Claude 等 AI 工具直接调用。

P—01

事实优于代码生成

fighorse 提供几何、样式、约束、组件关系和视觉参考，不把目标项目强行套进某个前端框架。代码由 AI 根据目标仓库自身结构生成。

P—02

可检查优于黑盒

AI 通过 MCP 调用的关键能力，都能用 CLI 复现和调试。结构化输出、诊断状态和导出清单让每一步都有证据。

P—03

授权优于默认写入

Figma 写入、本地文件导出、Code Connect 外发和 Canvas 脚本分别设门。读取是常态，修改必须明确授权。

03 / 主工作流

从链接到实现，
保持信号完整。

先缩小范围，再构建设计包；先读取真实资产，再实现；最后用视觉反馈验证。每一步都能被人和机器复查。

选择具体节点

复制准确的 frame、component 或 group 链接。团队或项目入口先走只读资源目录，不把整个 canvas 当作实现目标。

生成设计包

指定目标平台和资产格式，让 design package 输出精简结构、设计令牌、截图、诊断与导出计划。

项目原生实现

AI 使用设计事实，同时遵守目标仓库的框架、组件、测试和工程约定，不让 Figma 数据替代架构决策。

视觉闭环

捕获真实应用截图，与 Figma 参考比较，修复布局、排版、资产、裁剪和滚动问题，再记录可复用经验。

04 / Quick start

先用 CLI。
再接入 AI。

默认安装不会启动后台服务，也不会绑定端口。先完成一次可检查的命令行流程，需要时再启用共享 MCP 服务。

fighorse / install
# 构建并安装 CLI
$ cargo build --release
$ ./target/release/fighorse install --default --apply --source ./target/release/fighorse

# 保存令牌并验证
$ fighorse auth login --token <FIGMA_TOKEN>
$ fighorse quickstart
